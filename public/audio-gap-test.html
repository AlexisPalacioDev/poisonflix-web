Audio gap & dual-element probe

Diagnostic page. Open it on the phone that shows the bug, then run the tests in order. Use headphones or turn the volume up — some checks depend on what you hear.

Test 1 — Two elements at once

Plays a low tone and a high tone simultaneously on two separate elements. Does this platform allow concurrent audio at all?

Not run yet.

Test 2 — Crossfade with .volume

Low tone for 6s, then a 4s cross into the high tone by ramping volume on both. Listen for whether the two overlap smoothly or one cuts off.

Not run yet.

Test 3 — Gapless handoff with the screen locked

The important one. Plays a 25s low tone, preloads the high tone, and starts it 4s before the first ends — no silent gap. Press start, then lock the phone immediately. Keep it locked for about 40 seconds, then unlock and come back to read the log. It records everything that happened while you were away.

Not run yet.

Test 4 — Silent gap, for comparison

Same as test 3, but the second tone only starts after the first one ends — which is how the app behaves today. Lock the phone the same way. If test 3 survives and this one dies, the diagnosis is confirmed.

Not run yet.

Test 5 — Preloaded network audio, screen locked

Tests 3 and 4 both passed, but they cheated: the audio was generated in memory, so nothing was ever fetched. These last two use real multi-megabyte files over the network — which is what the app actually does.

Here the second file is fully downloaded before the screen locks. Press start, wait until it says ready, then lock the phone.

Not run yet.

Test 6 — Network fetch while locked (today’s behaviour)

The decisive one. The second file is not fetched until the first one ends — so the download has to happen with the phone already locked, exactly like the app does today. Press start and lock immediately.

If test 5 survives and this one dies, the bug is the background fetch, not the audio gap, and preloading is the fix.

Not run yet.

Test 7 — Deferred start, the way React does it

Tests 5 and 6 both survived, so the platform allows everything the app needs. The one thing they did differently from the app: they called play() straight from the native event handler. The app dispatches to a reducer and lets a useEffect call it — and React schedules passive effects through a MessageChannel, which is exactly the kind of callback a suspended process stops running.

This test defers the start the same way. If test 6 lives and this one dies, the bug is the deferral, not the platform. Press start and lock immediately.

Not run yet.
